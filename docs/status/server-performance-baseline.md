# 服务端性能基线（服务器壳：30 个终端、6 个事件流、2000 个对象的实时板）

> 状态：已验证记录。[补全架构](../design/completion-architecture.md) §11「服务端」，[执行计划](../design/completion-plan.md) G3-6。
> 脚本：`tools/probes/server-perf.mjs`（用法见[探针说明](../../tools/probes/README.md)）；比对基线：`tools/probes/server-perf-baseline.json`。

## 1. 场景

对一个真的服务器壳（`apps/server/out/main.js serve`，HTTPS 自签证书，临时数据目录与临时 HOME）按顺序加负载，每段量一次：

| 段       | 做什么                                                                                                                                 |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 空载     | 配对成管理员、建一个工作空间后静置 3 s                                                                                                 |
| 终端会话 | 逐个建 30 个 tmux 终端（`/bin/sh`），各自接上终端流                                                                                    |
| 事件扇出 | 6 条 `…/events` 订阅；对一块普通板 `PUT …/document` 40 轮，量从发请求到每个订阅者收到 `board.changed`                                  |
| 终端吞吐 | 30 个会话同时 `head -c 1MiB /dev/zero \| tr '\0' x`，量产生字节 / 墙钟与每个会话吐完的时间                                             |
| 实时板   | 客户端 A 一个事务写 2000 个便签节点（约 780 KiB 的更新）；在线客户端 B 收齐、新客户端 C 从零同步、读文档触发物化；A→B 单字段更新 40 次 |
| 稳态     | 以上全部挂着静置 5 s                                                                                                                   |
| 关终端   | 同时关掉 30 个终端，旁边每 20 ms 发一个轻请求（`GET …/boards`），记最慢一次——事件循环被堵住时所有客户端都在等                          |

RSS / CPU 是服务器壳进程自己的（`ps` / `/proc`），终端背后的 tmux 服务器另记一列。延迟都在同一台机器的回环上量，不含网络。

## 2. 环境

Apple M1 Max（10 核、32 GiB），macOS 26.6，Node 26.10.0，tmux 3.7c，2026-10-03。录制时这台机器上并行跑着其他工作包的构建与测试（load average 约 12–14），数字偏保守；同一时段负载冲到 100 以上的一次（§5）几乎每项都差了一倍以上。

`linux-x64`：GitHub Actions 的 `ubuntu-22.04` 托管运行器（x64），Node 22，夜间 B 档的 Linux 作业（§3.1）。

## 4. 发现的热点与修复

`--cpu-prof` 下跑一次，按自身耗时排序，排第一的不是业务代码，是 `spawnSync`：

| 调用链                                                                        | 自身耗时（一次完整运行） |
| ----------------------------------------------------------------------------- | ------------------------ |
| `terminate → terminateTree → processTree → processTable → execFileSync("ps")` | 1522 ms                  |
| `attach → getCapabilities → detect → execFileSync("tmux", ["-V"])`            | 169 ms                   |
| `create → ensureConf → renderedConf → defaultTerminal → spawnSync("infocmp")` | 104 ms                   |

三处都是同步子进程，跑的时候整个服务器壳的事件循环停住：关一个终端约 50 ms 里别的终端流、事件流、实时板都收不到任何帧；同时关 30 个，排在后面的请求要等一秒以上。修法（`ac5d2e34`）：

- `terminal/process.ts` 加 `readProcessTable()`（异步 `ps`）；`terminateTree` 与两个后端的 `getForeground` 改用它。休眠判据 `hibernator.ts::processesUnder` 后来也改成了异步（G5-16）；同步的 `processTable()` 只剩 Windows 上 `terminateTree` 的默认参数（那里不起 `ps`，表是空的）。
- tmux 后端的 `getCapabilities` 在探到「可用」之后按后端缓存（不可用时照旧每次重探，装上 tmux 之后能发现）。
- `defaultTerminal()` 每进程只问一次 `infocmp`。

修复前后（同一台机器、同一时段，各三次）：

| 指标                 | 修复前（`1b27e733`）  | 修复后（`ac5d2e34`）  |
| -------------------- | --------------------- | --------------------- |
| 同时关 30 个终端     | 3571 / 3930 / 3785 ms | 2438 / 2428 / 2387 ms |
| 关终端期间轻请求最慢 | 778 / 1110 / 1301 ms  | 174 / 83 / 139 ms     |
| 建会话 p50           | 53.8 / 43.1 / 47.8 ms | 34.8 / 37.9 / 31.6 ms |

修复后同一份 profile 里 `spawnSync` 只剩启动时的一次（集成检测）。关终端剩下的耗时是 `terminateTree` 发 SIGTERM 后每 100 ms 复查一次进程是否退出，以及每个终端一次异步 `ps` 的 fork 成本，不再堵事件循环。

## 5. 解读与没有改的

- **实时板的内存**：2000 个对象的板加载后 RSS 涨约 90 MiB，静置后不回落。在进程内对同样的负载强制 GC 后量 `heapUsed`，core 自己持有的文档只有约 12 MiB（与独立的 `Y.Doc` 实测一致）；其余是解码、落库、物化时的临时分配，V8 不把堆还给系统。不是泄漏，没改。
- **终端吞吐的上限在 tmux**：吞吐段 tmux 服务器占满近一个核（88%），服务器壳只用 35%。送到页面的字节数随 tmux 合并重绘而变（2.5–9 MiB 不等），所以吞吐按终端里产生的字节算，送达字节另记在 `result.json`。
- **扇出**：6 个订阅者的 `board.changed` 中位 1.3 ms、p95 2.2 ms，偶发 15 ms 左右的最大值与 GC 停顿同时出现；没有改的必要。
- **单字段更新**：逐条落库再转发，p50 0.4 ms。早期一版探针用 5 ms 轮询等结果，量出来的「5 ms」是轮询间隔；现在每收到一帧就唤醒等待者。
- **负载敏感**：同一时段机器负载冲到 100 以上时跑的一次，建会话 p95 219.6 ms、实时单字段更新 p95 19.3 ms、物化 240.9 ms，比对正确地判了 8 项退化。B 档的比较只在同一类机器上有意义。

## 6. 比对规则

- `server-perf-baseline.json` 按 `<平台>-<架构>` 存一份：`darwin-arm64`（本机，三次中位数）与 `linux-x64`（夜间 B 档的一次结果，§3.1；RSS 两项按三次中位数重录，§3.2）。没有该平台的基线时只报告不判。
- 一项算退化：比基线差 20% 以上，**并且**差值超过该项的绝对容差（`server-perf.mjs` 的 `METRICS`：如扇出 p95 10 ms、实时更新 p95 5 ms、RSS 40 MiB、关终端期间最慢 150 ms），免得 1 ms 对 2 ms 的噪声算成 100%。
- 重录基线时同步改这份文档的 §3。
