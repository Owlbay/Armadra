# ACP v2 调研（2026-10-09）

## 结论

- **ACP v2 没有正式发布。** 到今天，它仍处在 **Draft（草案）/ schema 预发布**阶段：最新是 `schema-v2.0.0-alpha.7`（2026-09-30，GitHub 标为 Pre-release）；稳定版是 `schema-v1.24.1`（标为 Latest）。官方 Rust schema 的 `ProtocolVersion::LATEST` 仍然是 `V1`，`V2` 要打开 `unstable_protocol_v2` feature 才有；TS SDK 只在 `@agentclientprotocol/sdk/experimental/v2` 子路径下提供 v2。官方明确要求在**版本协商加功能开关**之后再接入 v2，稳定前不要默认用于生产，也不要丢掉 v1。
- 我们用到的 7 家里，**只有 claude-agent-acp 0.88.0 能讲 v2**，而且要设环境变量 `CLAUDE_AGENT_ACP_EXPERIMENTAL_V2=1` 才开。其余各家实测都回 `protocolVersion: 1`。
- **现在不值得升级。** 建议先做零成本的准备工作（协商时容忍未知版本、给 v2 预留结构），等 v2 稳定、并且至少 codex-acp 和 opencode 支持后再分阶段实现。

## 2. v2 相对 v1 的变化（以官方迁移指南为准，草案仍可能改）

**版本协商**：机制不变。客户端在 `initialize` 里发自己支持的最高版本，Agent 支持就原样回，不支持就回它自己的最高版本，再由客户端决定继续还是断开。一条连接只讲一个版本。官方推荐 v1 和 v2 并存，每条连接各选一套。

| 领域 | v1 | v2 |
|---|---|---|
| initialize | `clientCapabilities`/`agentCapabilities`，`clientInfo`/`agentInfo` 可选 | 两边统一为 `capabilities` 和**必填**的 `info`；会话相关能力集中到 `capabilities.session.{prompt,mcp,delete,additionalDirectories}`；能力标记从布尔改成对象（`{}` 表示支持） |
| 会话基线 | `loadSession`、`sessionCapabilities.{list,resume,close}` 各自声明 | 只要声明了 `session`，就**必须**实现 new/list/resume/close/prompt/cancel/update；`session/load` **删除**，改用 `session/resume` 加 `replayFrom:{type:"start"}`；`session/delete` 仍可选 |
| prompt 生命周期（最大的破坏性变化） | `session/prompt` 的响应就是回合结束，带 `stopReason` | 响应只表示“已插入”，返回 `{messageId}`；回合进度和结束改由 `state_update`（`running`/`idle`/`requires_action`）报告，`stopReason` 放在 idle 那条里；新增 `error` 停止原因；插入之后的失败不再走 prompt 的错误响应；取消的确认是 idle 加 `cancelled` |
| 消息 | `messageId` 可选 | `messageId` 必填；新增整条消息的 upsert（`user_message`/`agent_message`/`agent_thought`），三态补丁语义：省略=不变，`null`=清空，给值=替换，chunk=追加 |
| 工具调用 | `tool_call` 创建 + `tool_call_update` 修改 | `tool_call` **删除**，第一次出现的 `tool_call_update` 即创建；新增 `tool_call_content_chunk`；status 多一个 `cancelled` |
| diff | `{path, oldText, newText}` | `{changes:[{operation:add/delete/modify/move/copy, path, oldPath?, fileType?, mimeType?}], patch?:{format:"git_patch", text}}`，无法机械地映射回 oldText/newText |
| 权限 | `{toolCall, options}` | 必填 `title`，可选 `description`，`subject` 是 `tool_call` 或 `command` 的联合；options 与响应形状不变；收到看不懂的 outcome 不得当作批准 |
| plan | `plan{entries}` | `plan_update{plan:{type:"items", planId, entries}}`，允许多个计划 |
| 模式 | `modes`、`session/set_mode`、`current_mode_update` | 全部**删除**，改用 config option（`category:"mode"`）；option 的 `id` 改名为 `configId` |
| fs / terminal | 客户端提供 `fs/*`、`terminal/*` | 全部**删除**；新增由 Agent 拥有的只读显示终端：`terminal_update`、`terminal_output_chunk`，内容为 base64 |
| MCP | stdio 配置没有 `type`；支持 sse | 必须带 `type` 判别字段；**去掉 SSE**；能力拆成 `session.mcp.stdio` 和 `session.mcp.http` |
| 认证 | `authenticate`、`logout`，方法字段叫 `id` | 改为 `auth/login`、`auth/logout`；字段改叫 `methodId`，`type` 必填；终端认证的 `env` 改成 `[{name,value}]` 数组 |
| slash 命令 | `input:{hint}` | `input:{type:"text",hint}`；`session/new`/`resume` 的响应里可以直接带 `availableCommands` |
| 内容块 | 5 种 | 5 种不变；字段对齐最新 MCP；`resource_link` 多了 `icons` |
| 扩展性 | `_meta`、`_` 前缀方法 | 所有枚举和联合都开放；`_` 前缀留给各实现自定义，其他未知值留给协议将来用，收到后应保留或安全降级 |
| 传输 | stdio NDJSON | 不变，但必须接受 JSON-RPC batch 数组 |

## 3. 适配器 / CLI 对 v2 的支持（2026-10-09 实测）

测法：在 `/tmp` 下向每个程序只发一条 `initialize{protocolVersion:2, info, capabilities:{}}`，读回它答的版本。没有开会话，也没碰仓库和 Armadra 数据目录。

| 我们的条目 | 程序与版本 | 答的版本 | 证据 |
|---|---|---|---|
| claude | `@agentclientprotocol/claude-agent-acp` 0.88.0 | 默认 **1**；设 `CLAUDE_AGENT_ACP_EXPERIMENTAL_V2=1` 后为 **2**（响应改用 `info`/`capabilities`） | `dist/serve.js` 里 `acpProtocolRouter().withV1().withV2()`；`dist/index.js` 读这个环境变量；PR #1217（2026-10-01 合入，0.86.0 起可用）以及后续 #1219–#1256 |

## 4. 对照我们代码的升级改动面

### 4.1 协议层在 `@armadra/agent/acp`（armadra-agent 仓库），不在本仓库

- `armadra-agent/src/drivers/acp/types.ts:15`：`ACP_PROTOCOL_VERSION = 1 as const`。
- `armadra-agent/src/drivers/acp/client.ts:156-176`：`initialize` 发 v1 形状（`clientCapabilities.fs/terminal`、`clientInfo`），并且**严格要求** `result.protocolVersion === 1`，否则直接抛错。这对现状是安全的：v2 Agent 收到 1 会回 1。
- `client.ts:178-192`：`supportsResume/Load/List/Close/Images` 读的都是 v1 的能力字段。
- `src/drivers/acp/testing/fake-agent.ts:347`：假 Agent 只讲 v1。本仓库的 `acp-e2e` 和单测都依赖它。
- Agent 侧 `src/modes/acp/acp-server.ts:266-270`、`acp-auth-gate.ts:180-185`：ama 作为 Agent 只回 1。

### 4.2 本仓库 core（`apps/desktop/src/core/acp/`）

- `host.ts:266-283` `capabilitiesOf`：v1 字段，需要按版本拆成两套（v2 读 `capabilities.session.*`，`load` 恒为 false，`resume/list/close` 由基线保证；`authMethods` 读 `methodId`）。
- `host.ts:287-298` `resumeMethod` 与 `host.ts:368-400`：`load` 分支在 v2 下要改成 `resumeSession(id, cwd, {replayFrom:{type:"start"}})`；`mcp.ts:113-163` 的 `loadSession` 同样要改。
- `host.ts:363,380,385,409,427,610-620` 以及 `adapters.ts:40,66,104-218,250-269`：权限模式落在 `modes`/`session/set_mode` 上。v2 删掉了这一套，`modeId` 需要映射到 `configId:"mode"` 的 config option（`session.ts:506-523` 的 `setMode`、`session.ts:621-626` 的 `current_mode_update` 也一样）。
- `session.ts:429-466` `runTurn`：**最大的改动点**。现在用 `await prompt()` 的返回值结束回合；v2 下 prompt 一返回 `messageId` 就算插入成功，回合结束要等 `state_update(idle)`，取消也靠这条确认（`session.ts:497` 起的 `cancel`）。另外 `session.ts:439-449` 自己合成了一条 `user_message_chunk`，v2 下 Agent 会回一条带同一 `messageId` 的 `user_message`，需要去重。
- `session.ts:325-335`（`plan`）、`session.ts:650-653`（`tool_call`）、`normalize.ts:60-175`（stopReason 和信号）：update 的变体名要跟着改。
- `mirror.ts:146-181,262-300`：镜像把 `tool_call` 转成 `tool_use`，diff 读 `oldText/newText`。v2 要改为按首次出现的 `tool_call_update` 创建，diff 从 `changes` + `patch.text` 取。
- `client.ts`（桌面，`AcpPendingPermission.toolCall` 约 88-94 行）以及审批行：v2 的权限请求带 `title/description/subject`，`subject` 可能是 `command`，也可能缺失。
- `elicitation.ts`：elicitation 在 v1 已经稳定，v2 形状基本延续，需要对一遍 schema。

### 4.3 共享类型与页面

- `packages/shared/src/api/acp.ts:244-252`：diff schema 是 `oldText/newText`；`:334-341` 的 `ACP_STOP_REASONS` 没有 `error`；`:578` 和 `:671` 的 `modes`/`AcpSessionMode` 是 v1 概念。`:331` 的 `acpSessionUpdateSchema` 只校验判别字段，好处是 v2 的新变体能原样转发。
- `apps/web/src/acp/store.ts:390-420`：只处理 `agent_message_chunk`/`tool_call`/`plan`/`current_mode_update`；`SessionView.tsx:232` 靠 `_chunk` 后缀跳过。要补 `agent_message`/`user_message` 整条 upsert、`tool_call_content_chunk`、`plan_update`、`state_update`、`terminal_update/terminal_output_chunk`。
- 推荐做法：**在 core 里把 v2 归一成内部的 v1 形状**（或一个中立形状）再交给页面和镜像，这样页面与 `docs/contracts/core-json-api.md` §14 的线上形状基本不用动；新增能力（结构化 diff、显示终端）另开新节号登记。

### 4.4 配套

- `tools/release/compatibility.json` 的 `acp.protocolVersion: 1` 只是一个数字，`adapters.test.ts:106-109` 断言它等于 1。并存两版时建议改成 `protocolVersions: [1, 2]`，或按适配器记录 `verified.v2`。
- 契约：新增节号描述 v2 归一规则，不复用已有的 §14 和 §26。

### 4.5 能否同时支持 v1 和 v2

**可以，协议本身就是为此设计的。** 一条连接在 `initialize` 后只讲一个版本：客户端发 2，Agent 回 1 就走 v1 栈，回 2 就走 v2 栈。实现上需要：

1. 把 armadra-agent 的 `AcpClient` 拆成 v1 和 v2 两个薄协议面，共用 JSON-RPC peer；`initialize` 改成接受 `{1,2}`，回别的值仍然拒绝。
2. 本仓库 `host.ts` 按 `capabilities.protocolVersion` 选一个 normalizer，把 v2 归一后交给 `session.ts`、`mirror.ts`、页面。
3. 用开关控制：按适配器 opt-in，默认只发 1，比如在 `adapters.ts` 里加一个 `protocol: { max: 2, env?: {...} }`。claude 需要额外注入 `CLAUDE_AGENT_ACP_EXPERIMENTAL_V2=1`。

### 4.6 风险

- **草案还会变**：alpha.1 到 alpha.7 两个半月里改了 7 次（tool call name、cancelled、messageId 返回、availableCommands 等），现在跟进会被反复改动拖着走。
- **对端几乎没有**：只有 claude 能用，而且是实验开关；codex 合入后又回滚了，说明上游自己也没定下来。
- **回合语义变化影响很大**：`working/done` 状态、Eco 休眠、投递排队（`send` 要等 idle）、审批 `blocked`（可以借 `requires_action` 改善）、`acp.turn` 事件都以“prompt 响应就是回合结束”为前提。
- **数据**：镜像里 v1/v2 的 diff 形状不同，持久化前要归一；不能把 `terminal_output_chunk` 的原始终端字节写进镜像或日志（AGENTS.md 把它算 P0）。
- **fs/terminal 删除**：对我们没影响，我们本来就发 `fs:false, terminal:false`。

## 5. 测试计划（等真正实施时）

1. **单测**：在 armadra-agent 的 `fake-agent.ts` 里加 `--protocol 2` 模式（state_update、messageId、tool_call_update 创建、plan_update、结构化 diff、权限 subject、resume 加 replayFrom）。本仓库 `host.test.ts`、`session.test.ts`、`mirror.test.ts`、`normalize.test.ts`、`features.test.ts` 每个用例在 v1 和 v2 下各跑一遍；协商用例覆盖“发 2 回 1”“发 2 回 2”“回 3 拒绝”。
2. **A 档 `tools/probes/acp-e2e.mjs`**：假 Agent 加 v2 参数，同一套 7 步各跑一遍（回合 done、审批拒绝、投递、elicitation/模型、驱动切换接回、Eco 唤醒）。
3. **C 档 `agent-e2e/scenario-12-acp.mjs`**：claude 用 `CLAUDE_AGENT_ACP_EXPERIMENTAL_V2=1` 真跑 v2，其余家仍走 v1，确认降级正确；用 `--record-compat` 把 `compatibility.json` 记成按版本区分的 verified 区间，比如 `claude.verified.v2.min = 0.86.0`（以真跑结果为准，只扩不缩）。
4. 回归：`pnpm libs:build && pnpm --filter @armadra/desktop test`、`pnpm --filter @armadra/web test/typecheck`、`pnpm check`。

## 6. 建议与分阶段

**现在不升级。** v2 是草案，生态里只有 claude 实验性支持，升级的收益接近零，而回合语义的重写成本高、风险也高。

- **阶段 0（现在可以做，小改动，可选）**：armadra-agent 的 `initialize` 保持发 1；把“严格等于 1”的报错文案和 `acp_protocol_version` 的诊断改清楚。`compatibility.json` 结构暂时不动。另外订阅 agent-client-protocol 的 releases，关注 `schema-v2.0.0` 正式 tag 和 `ProtocolVersion::LATEST` 改成 V2 的提交。
- **阶段 1（触发条件：v2 schema 出 RC 或正式版，或 codex-acp 正式带上 v2）**：在 armadra-agent 实现 v2 客户端协议面并扩展假 Agent；本仓库加 v2 normalizer（归一成内部形状），按适配器开关 opt-in，先只开 claude；补齐单测和 A 档。
- **阶段 2（v2 稳定，且至少 claude/codex/opencode 三家默认支持）**：默认发 2、自动降级到 1；页面接入 v2 的增量能力（结构化 diff、显示终端、`requires_action` 驱动 blocked 状态、多 plan）；契约新增节号；C 档按版本记录 verified。
- **阶段 3（可选）**：ama 作为 Agent 侧接入 v2（用 SDK 的 `agentProtocolRouter` 或自己实现），v1 继续保留。
